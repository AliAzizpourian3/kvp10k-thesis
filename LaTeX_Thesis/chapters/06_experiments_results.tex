\section{Overview and Chapter Structure}
\label{sec:story-overview}
% ---------------------------------------------------------------------------

This chapter reports the experiments and results of the thesis. Each experiment
was motivated by the findings of the previous one, forming a chain from a
generative baseline to a corrected discriminative model and an assessment of
where it stands relative to the published KVP10k benchmark.

The experiments proceed as follows. We begin with a generative reference
baseline (Mistral-7B) and then evaluate a layout-aware discriminative approach
(LayoutLMv3). We investigate two linking granularities and use validation-based diagnostic
experiments to identify three compounding data-pipeline problems. The final
corrected V4 combines those pipeline fixes with correct scheduler accounting,
full-state resumption, class-aware entity metrics, validation pair-F1 checkpoint
selection, and aligned early stopping.

\subsection*{Evaluation Setup}

All official benchmark comparisons use the same evaluation set:
\textbf{581 unique test pages}
from the KVP10k test split (55\% of 1{,}051 unique pages; limited by PDF
download failures and scanned pages without text layers). The evaluation
follows IBM's released KVP10k benchmark implementation. Matching is greedy and
one-to-one, requires equal KVP types, and uses NED $<0.2$ for text. The paper
describes the location criterion as IoU $>0.3$, whereas the released code uses
IoU $\geq0.3$; benchmark-comparison results follow the executable code and
record this discrepancy. Precision and recall are calculated per page and
macro-averaged over pages with non-empty ground truth after category filtering;
F1 is the harmonic mean of the two macro averages. Results are reported for
regular KVPs, unkeyed values, unvalued keys, and their aggregate, under
text-only, location-only, and combined matching. Pooled regular-link counts
used during V1--V4 diagnosis are identified separately and are not compared
directly with the published macro scores; those diagnostics use explicitly
stated subsets and are not full-test benchmark results. Preprocessing and
input-text differences are described in Section~\ref{sec:data-preprocessing}.

\section{Experiment 1: Generative Baseline (Mistral-7B QLoRA)}
\label{sec:exp1}
% ---------------------------------------------------------------------------

\subsection*{Setup}

The starting point of the experimental work is a generative re-implementation
of the approach used in the KVP10k paper; it is not a strict reproduction.
Mistral-7B-Instruct-v0.2 is fine-tuned with 4-bit QLoRA (NF4 quantisation,
LoRA rank $r=4$, $\alpha=4$) on LMDX-formatted document prompts, where each
line-like text block is represented as \texttt{text x1|y1|x2|y2} in normalised
coordinates. The model generates KVP predictions as structured text
output. It is trained for a fixed eight epochs with learning rate
$5 \times 10^{-4}$ using only the prepared training data. After training is
complete, the final model generates predictions for the 581 prepared held-out
test pages, which are then scored with the released KVP10k evaluator.

The exact prompt template is shown in Figure~\ref{fig:stage3-prompt}. It follows
the LMDX paradigm~\cite{lmdx} used by the KVP10k baseline --- a document
representation with text-block coordinates followed by a task instruction
requesting a Python list-of-lists output. Because Naparstek et al.\ do not
publish their prompt, we reproduce its format and output contract rather than a
verbatim string. The reconstruction differs from the published system in
several respects. Word text and coordinates come from PyMuPDF's native text
layer rather than Tesseract OCR; pages without a usable text layer are
excluded; the resulting train and test subsets differ; the unpublished prompt
is reconstructed; LoRA rank is limited to $r=4$; and the paper does not report
enough training detail to reproduce its setup exactly. Numerical proximity
must therefore be read as an indicative comparison, not evidence of strict
reproduction.

\section{Experiment 2: Layout-Aware Entity Classification (Stage 4a)}
\label{sec:exp2}
% ---------------------------------------------------------------------------

\subsection*{Setup}

We introduce LayoutLMv3-base (125M parameters) as the document encoder.
The reported runs use extracted text and bounding boxes, with no
document-specific page image content; the image input is a blank placeholder.
In Stage~4a, the LayoutLMv3 encoder and entity classifier are trained with the
linker disabled:
for each token, the model predicts whether it is a Key, Value, or Other token.
This phase provides an entity-oriented initialization before the more complex
linking task is introduced.

\subsection*{Result 2: Historical Result Unavailable}
\label{sec:res2}

The original Stage~4a checkpoint no longer survives. Its historical validation
score was calculated with the legacy entity metric, which did not fully
penalise confusion between Key and Value labels. Because the saved training
history contains no predictions or class-aware confusion counts, that score
cannot be corrected after the fact and is therefore omitted. Stage~4a is
retained here to document the entity-pretraining phase, but no corrected
Stage~4a entity result is claimed. Corrected class-aware entity performance is
reported for the final corrected V4 checkpoint.

Unlike Mistral, the discriminative model can only predict labels for tokens
that appear in the document; it has no mechanism for generating text absent
from the extracted input. It can, however, still assign the wrong label to an
observed token.

\textbf{Motivation for Experiment 3:} Stage~4a provides the entity-pretraining
phase; Experiment~3 then introduces the relation-linking task of pairing
predicted keys with their corresponding values.

\section{Experiment 3: Token-Level Linking (V1)}
\label{sec:exp3}
% ---------------------------------------------------------------------------

\subsection*{Setup}

We activate the projected scaled-dot-product linker with spatial features, trained jointly with the entity classifier.
In V1, linking operates at the \textbf{token level}: each key token is scored
against each value token, producing a dense adjacency matrix of size
$N_{key} \times N_{value}$. For illustration, a page with $\sim$100 key tokens and
$\sim$100 value tokens produces $\sim$10{,}000 candidate pairs with
only $\sim$20 true positives (approximately $500{:}1$ neg:pos). A
\texttt{pos\_weight} of up to 50 is applied to the binary cross-entropy loss
to counteract the imbalance. A $\lambda$ sweep over $\{0.5, 1.0, 2.0\}$
controls the relative weight of the linking objective.

\subsection*{Result 3: Token-level candidates are highly imbalanced}
\label{sec:res3}

The seed-42 validation diagnostics use the preserved V1/V2 development
checkpoints only to inspect candidate formation, score distributions, and span
availability. These are internal diagnostics, not official benchmark results.
The token-level formulation produces a dense candidate matrix with very few
positive relations, which motivates span-level linking.

\textbf{Motivation for Experiment 4:} One motivation for V2 is to reduce the
candidate space by grouping contiguous key and value tokens into spans before
relation scoring. In this illustrative example, the candidate space decreases
from $\sim$10{,}000 to $\sim$225 entries. With 15 positive links, the
illustrative 225-candidate case has
210 negatives, or approximately $14{:}1$.

\section{Experiment 4: Span-Level Linking (V2)}
\label{sec:exp4}
% ---------------------------------------------------------------------------

\subsection*{Setup}

In V2, contiguous same-label tokens are grouped into spans, and the linker
scores key spans against value spans. In the illustrative example above, this
reduces the candidate space from about 10{,}000 token pairs to 225 span pairs.
With 15 positive links, the 210 remaining candidates are
negative, which gives a ratio of approximately $14{:}1$.
The original V2 implementation warm-started from the best Stage~4a checkpoint,
but span grouping used \texttt{argmax} predicted entity labels rather than
ground-truth labels; the effect of this choice is examined in
Experiments~5--7.

\subsection*{Result 4: Span-level linking requires pipeline diagnosis}
\label{sec:res4}

The span-level formulation reduces the candidate space, but the validation
diagnostics still show problems in span availability and relation supervision.
These findings motivate the focused validation analyses in Experiments~5--7.

\section{Experiments 5--7: Diagnostic Analysis (D1, D2, D3)}
\label{sec:exp567}
% ---------------------------------------------------------------------------

\subsection*{Setup}

Three targeted validation diagnostics were used to investigate why V2 remained
ineffective despite the reduced candidate imbalance:

\paragraph{D1 --- Link score distribution.}
Raw linker logits were extracted from the preserved V2 checkpoint on 200
documents from the fixed seed-42 validation split. The 1{,}481 candidate-pair
logits have a median of $-6.93$ and a mean of $-7.59$. Only 36 candidate pairs
have sigmoid probability at least $0.5$, and only 20 best-per-key predictions
reach this threshold.

\paragraph{D2 --- Entity span analysis.}
This diagnostic compares predicted entity token and span counts before and
after bounding-box validity filtering in the span grouping function for each
document.

\paragraph{D3 --- Link label audit.}
This diagnostic traces the full link label generation pipeline from ground-truth
KVPs through word-level labels, token-level alignment, and span-level collapse.

\subsection*{Result 5--7: Three Compounding Bugs Identified}
\label{sec:res567}

\paragraph{Bug 1 --- Missing Teacher Forcing.}
Inspection of the training path showed that the original V2 linker formed spans
from \texttt{argmax} entity predictions while relation labels came from
ground-truth annotations. Entity
errors therefore misaligned the predicted spans and relation supervision.
\emph{Fix: use ground-truth spans during training and predicted spans during
inference.} This corrects training-label alignment, although the different span
sources at training and inference remain a methodological limitation. The
validation diagnostics also showed that other pipeline defects remained.

\paragraph{Bug 2 --- Bounding Box Filter (D2).}
The \texttt{group\_contiguous\_spans} function applied the strict predicate
$(x_1 < x_2) \wedge (y_1 < y_2)$, but quantisation to the LayoutLMv3
$[0, 1000]$ coordinate grid can produce valid tokens whose boxes have zero
width or zero height. Across the 200 validation pages, the predicate removed
47.5\% of predicted KEY tokens and 48.5\% of predicted VALUE tokens. Only 81
pages retained both strict key and value spans. \emph{Fix: the corrected
grouping rule excludes only positions with $[0,0,0,0]$, such as special or
padding positions.}

\paragraph{Bug 3 --- Link Label Cross-Product Explosion (D3).}
The label function \texttt{\_generate\_labels} created a link label for
\emph{every} key-word index $\times$ \emph{every} value-word index within a
KVP. This inflated the token-pair label matrix. After span-level collapse,
this made the span-level supervision much denser than intended and reduced its
ability to distinguish the annotated relation from other candidate span pairs.
\emph{Fix: generate one representative word-level link per recovered ground-truth KVP.}

  \label{tab:diagnostic-verification}
  \begin{tabular}{@{}p{5.2cm}p{4.0cm}r@{}}
    \toprule
    \textbf{Quantity} & \textbf{Unit} & \textbf{Count} \\
    \midrule
    Ground-truth Regular KVPs & KVP pairs & 79 \\

not an ablation, and therefore cannot attribute effects to any single
correction. In V4, all three corrections are applied jointly. The reported V4
results therefore demonstrate pipeline repair as a whole rather than each
correction's independent numerical contribution; isolating individual effects
requires dedicated ablations outside the scope of this thesis.

\section{Experiment 8: Final Corrected Model (V4)}
\label{sec:exp8}
% ---------------------------------------------------------------------------

\subsection*{Setup}

The final V4 uses the LayoutLMv3-base encoder, entity classifier, span-level
projected scaled-dot-product linker with spatial features, prepared data, and
seed-42 split established during development. It uses batch
size 1, gradient accumulation 8, learning rate $2\times10^{-5}$, linker-loss
weight 5.0, maximum 30 epochs, and early-stopping patience 10. No rendered page
image is loaded. Every sample receives the same constant blank visual input, so
the experiment does not evaluate document-specific image features.

The run is warm-started from Canary~B rather than trained from scratch. It
loads all 226 compatible entries: 212 from the encoder, 2 from the entity
classifier, and 12 from the linker. Scheduler length is calculated from 607
optimizer updates per epoch, and the 500 warm-up steps are optimizer steps.
Each epoch checkpoint contains the full state required for exact resumption.

The V4 decoder uses a fixed linker-confidence threshold of $0.5$ when producing
key--value pairs. The released evaluator assesses those predictions using NED
$<0.2$ and IoU $\geq0.3$. Checkpoint selection and early stopping use official
validation Regular text+location macro pair F1 and only validation data. The
selected checkpoint is evaluated on the test set after selection. Test results do not affect checkpoint selection.

does not determine checkpoint selection. Because the corrections were applied
together, their independent contributions were not isolated.
